## 2. Otorisasi menu: backend vs sidebar

**Penting — otorisasi backend NYATA ada**, bukan hanya cek tampilan di blade:
- `App\Http\Middleware\EnsureUserHasRole` (`app/Http/Middleware/EnsureUserHasRole.php:17-24`) — `abort(403)` bila role user tidak ada di daftar `role:...` middleware route.
- `App\Http\Middleware\EnsureUserHasMenuAccess` (`app/Http/Middleware/EnsureUserHasMenuAccess.php:18-28`) — `abort(403)` bila key menu tidak ada di `config('akses.menu')[role]`, dipasang di beberapa route dashboard (`menu-akses:dashboard`, dll, lihat `routes/web.php:55-81`).
- Kedua middleware ini membaca role dari `App\Helpers\GuestSession::role()` (`app/Helpers/GuestSession.php:29-32`), bukan langsung dari sidebar — sidebar (`layouts/app.blade.php:26-27`) memakai fungsi role/config yang **sama persis**, sehingga tampilan menu dan penegakan akses selalu konsisten by construction (satu sumber kebenaran: `config/akses.php` + `GuestSession::role()`).

Route-route data-sensitif (npd, spm, users, pelimpahan, manajemen-data, pengembalian) selalu dibungkus middleware `role:` eksplisit di `routes/web.php` (dikutip lengkap di §0 hasil pembacaan; lihat juga tabel per-menu di §3) — **tidak ditemukan** menu yang otorisasinya HANYA ada di blade/sidebar tanpa middleware backend. Ini bukan temuan keamanan negatif untuk kasus umum.

**Satu pengecualian by-design yang perlu dicatat** (bukan celah, tapi perlu didokumentasikan): route `GET /sp/input`, `POST /sp/input`, `GET /surat-perintah/monitoring`, `GET /tunjangan-keluarga/perubahan`, `POST /tunjangan-keluarga/perubahan` **sengaja publik** (di luar grup `auth.or.guest`, `routes/web.php:42-52`), untuk role "layanan" yang memang tidak pernah login. Dibahas risikonya di §3.6/§3.7 dan §6.

## 3. Detail per Menu/Submenu

### 3.1 Manajemen Users
- **Route & verb**: `GET/POST /users`, `GET /users/create`, `GET /users/{user}/edit`, `PUT /users/{user}`, `PATCH /users/{user}/username`, `PATCH /users/{user}/toggle-aktif`, `DELETE /users/{user}` (`routes/web.php:97-104`).
- **Controller@method**: `UserController::index/create/store/edit/update/updateUsername/toggleAktif/destroy` (`app/Http/Controllers/UserController.php:19-218`).
- **View**: `resources/views/users/{index,create,edit,_form}.blade.php`.
- **Role**: middleware `role:superadmin` (`routes/web.php:96`). Tambahan in-controller: `UpdateUsernameRequest::authorize()` (`app/Http/Requests/UpdateUsernameRequest.php:11-18`) — superadmin tidak boleh mengubah username miliknya sendiri lewat endpoint ini.
- **Tabel dibaca/ditulis**: `users` (RW), `pegawai` (R, untuk dropdown & auto-isi NIP), `audit_log` (W).
- **Logika inti**: normalisasi username lowercase; `role` harus salah satu `User::ROLE_OPTIONS` (10 role, semua kecuali `layanan` — `app/Models/User.php:31-42`); NIP dipaksa ikut data `Pegawai` bila `pegawai_id` diisi (mengabaikan NIP manual); **invarian "minimal 1 superadmin aktif"** ditegakkan di `update`/`toggleAktif`/`destroy` via `kunciSuperadminAktif()` yang mengunci (`lockForUpdate`) semua baris superadmin aktif sebelum mengecek (`app/Http/Controllers/UserController.php:198-217`) — mencegah race dua request menonaktifkan superadmin terakhir bersamaan; user tidak bisa menonaktifkan/menghapus dirinya sendiri.
- **Validasi**: inline `Request::validate()` (username regex `/\A[a-z0-9._-]+\z/`, unique; role `Rule::in`; nip unique; password min 6); `UpdateUsernameRequest` menambah re-autentikasi `current_password`.
- **Efek samping**: `AuditLog::catat` di setiap aksi mutasi (Tambah/Ubah/Ubah Username/Aktifkan/Nonaktifkan/Hapus User).
- **DB::transaction**: Ya untuk `update`, `updateUsername`, `toggleAktif`, `destroy`. Tidak untuk `store` (single insert, wajar).
- **Test**: `tests/Feature/UsernameManagementTest.php`, `tests/Feature/RoleAccessMatrixTest.php`.

- **Efek samping**: `AuditLog::catat('Ubah Profil', ...)`.

Riwayat penting: `RakBulananDuplicateAudit` dan migrasi `2026_07_26_090000_restructure_rak_bulanan_key.php` mengindikasikan **insiden/nyaris-insiden masa lalu** terkait skema RAK yang di-key per Tagging (bisa menghasilkan banyak seri RAK berbeda untuk satu Sub Kegiatan+Kode Rekening yang seharusnya sama) — migrasi perbaikannya sengaja *resumable* dan **berhenti keras (bukan menebak/menggabung otomatis)** bila menemukan duplikat/konflik identitas, diuji oleh `RakBulananMigrationRecoveryTest`.

**Gap kecil**: tidak ada aksi `batalkan()`/cancel untuk NPD Historis maupun Tunjangan Keluarga (Master Anggaran & RAK punya). Batch staging yang ditinggalkan hanya menumpuk sampai `expires_at`/kedaluwarsa — bukan risiko data produksi, hanya housekeeping.

### 4f. Penomoran NPD

**Dikonfirmasi langsung dari skema DB (`SHOW CREATE TABLE npd`)**: ada `UNIQUE KEY npd_keu_tahun_nomor_urut_unique (keu, tahun, nomor_urut)` — **proteksi race condition di level database benar-benar ada**, bukan sekadar `SELECT MAX+1`.

Mekanisme lengkap (`NpdController::transisi()`, aksi `verifikasi`, `app/Http/Controllers/NpdController.php:163-180, 204-218`):
1. `nomor_urut` **diinput manual oleh Verifikator** (1-999), bukan auto-increment/MAX+1.
2. Cek bentrok optimistik di luar transaksi, lalu **cek ulang dengan `lockForUpdate()` di dalam `DB::transaction`**.
3. **Backstop**: unique index DB. Bila dua transaksi tetap lolos cek aplikasi secara bersamaan (celah teoritis: lock hanya mengunci baris yang SUDAH ADA dengan nomor itu, bukan "ketiadaan" nomor tsb), `save()` akan melempar `QueryException` pelanggaran unique, yang ditangkap dan diubah jadi pesan error ramah ("Nomor NPD baru saja dipakai...") alih-alih 500 (`:226-231`).

**Verdict**: bukan "hanya SELECT MAX+1 tanpa proteksi" — ada 3 lapis (input manual + lock + unique index DB). Kelemahan yang tersisa hanya teoritis (race pada nomor yang sama-sama belum pernah dipakai, diserap oleh unique index sehingga hasil terburuknya adalah salah satu user mendapat pesan error untuk input ulang, **bukan** duplikasi data tersimpan). **Catatan untuk audit**: tidak ada test konkuren/paralel yang membuktikan skenario race sesungguhnya — hanya pembuktian statis + constraint DB.

Semua bagian lain sudah diverifikasi dengan membaca file sumber (bukan menyimpulkan dari nama method), termasuk cross-check langsung ke skema database aktual (bukan hanya migrasi) via `SHOW CREATE TABLE`/`SHOW TABLES`/`SELECT COUNT(*)` read-only.
